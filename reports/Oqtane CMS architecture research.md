# Oqtane trades page-builder polish for plumbing

Oqtane is best understood not as a WordPress/Gutenberg competitor but as a **DotNetNuke-descended application framework** that happens to ship CMS features: its creator, Shaun Walker, also created DNN, and Oqtane's explicit design goal was fixing DNN's "widely acknowledged core limitations" — automated upgrades and tenancy isolation by name ([Oqtane Blog: Oqtane vs DNN](https://www.oqtane.org/blog/!/19/)). The framework's real engineering depth shows up in infrastructure — a genuinely dynamic (if restart-gated) module-loading system, a hybrid database-per-tenant/row-per-site multi-tenancy model, and a runtime-composed permission-policy system — not in its content-editing UX, which is a dropdown-and-menu-driven "content editor" with no drag-and-drop, no page-level draft/versioning, and a Quill 1.3.7 rich-text editor pinned to a years-old release. For a single-tenant Blazor Server business suite already running its own page editor, almost nothing in Oqtane's page-building UX is worth copying, but three infrastructure ideas are genuinely transferable in isolation: the `IModule`/`ITheme` interface-plus-reflection extension pattern, the multi-alias-per-site hostname/path resolution table (useful even without full multi-tenancy), and the dynamically-composed `EntityName:PermissionName:DefaultRoles` authorization-policy model for delegated admin. Several factual points in the underlying research remain genuinely unresolved — a conflicting description of module database migrations (EF Core vs. a "DbUp" SQL-script mechanism), unverifiable contributor/release-count statistics, and a stray 2024-vs-2026 date discrepancy on the latest release — and are flagged rather than silently resolved below.

## Core pitch is "infrastructure so you don't have to," current on .NET 10, weekly-cadence maintenance releases

Oqtane's own README frames it as "an open source Content Management System (CMS) and Application Framework," with the tagline "Build Applications, Not Infrastructure" ([GitHub README](https://raw.githubusercontent.com/oqtane/oqtane.framework/master/README.md)), while its marketing site separately calls it "rocket fuel for Blazor" and GitHub's own repo description now calls it "an open-source developer productivity platform for building modern .NET applications and websites that run on Web, Desktop and Mobile" ([oqtane.org](https://www.oqtane.org); [GitHub search result](https://github.com/oqtane/oqtane.framework)). The three self-descriptions drifting from "CMS" toward "general app platform" is a real positioning shift, not just marketing noise — it lines up with .NET MAUI (desktop/mobile hybrid) support having been added to the roadmap. Hosting-wise, Oqtane exposes all of Blazor's render/runtime combinations — Static SSR, Interactive Server, Interactive WebAssembly, Interactive Auto, and MAUI Blazor Hybrid — through its own vocabulary layer ("render mode": Interactive/Static/Headless; "runtime": Server/WebAssembly/Auto) that does not map 1:1 onto Microsoft's own `InteractiveServer`/`InteractiveWebAssembly`/`InteractiveAuto` terms ([Oqtane Docs: Render Modes](https://docs.oqtane.org/guides/concepts/render-modes/index.html)). Tellingly, Oqtane's own docs recommend against the flashiest option: Auto runtime is explicitly called out as **"does not work as expected" and not recommended**, with the documented defaults being Static+Server for websites and Interactive+Server for web applications ([Oqtane Docs: Render Modes](https://docs.oqtane.org/guides/concepts/render-modes/index.html)). That caveat is dated November 2024 in the docs with no visible revision timestamp since, so whether it's still true in the current 10.2.x line is **unconfirmed** — flagged here as possibly-stale documentation rather than a resolved defect.

What actually ships in a fresh install is thinner than the marketing implies. The real, pluggable `Oqtane.Client/Modules` folder in the current source tree contains only **HtmlText** as a genuine content module, alongside internal Admin/Controls/Enums scaffolding — no blog, gallery, or forum modules are bundled ([GitHub: Oqtane.Client/Modules tree](https://github.com/oqtane/oqtane.framework/tree/master/Oqtane.Client/Modules)). Oqtane's own Modules Overview documentation page, fetched directly, gave **no concrete list of shipped modules at all**, gesturing only at hypothetical categories ("photo galleries, blogs, rotators, forms") — a real gap in Oqtane's own docs, not a research shortfall ([Oqtane Docs: Modules Overview](https://docs.oqtane.org/guides/modules/index.html)). Site/user/page/file management lives in the framework's built-in Admin system rather than as a separate content module. As of this research the current release is **v10.2.6**, targeting **.NET 10**, published September 14, 2026, confirmed by two independent fetches (the release-tag page and the releases index) ([GitHub Release v10.2.6](https://github.com/oqtane/oqtane.framework/releases/tag/v10.2.6); [NuGet: Oqtane.Framework 10.2.6](https://www.nuget.org/packages/Oqtane.Framework)) — one intermediate WebFetch summary stated "September 14, 2024" instead, a discrepancy the research explicitly flags rather than silently discards, though 2026 is corroborated by two independent sources and matches the surrounding date context. The 10.2.x line has shipped roughly seven point releases between May and September 2026 (10.2.0's "major" feature drop — FusionCache integration, Site Groups with content sync, Copy Page — followed by a stabilization tail of bugfix/security releases through 10.2.6), a pattern of one feature release followed by hardening releases worth knowing before planning an upgrade ([GitHub Releases page](https://github.com/oqtane/oqtane.framework/releases)). The project is an official **.NET Foundation member project**, MIT-licensed with copyright held by the Foundation rather than a company, and shows sustained multi-year activity, though the current GitHub snapshot (2.3k stars, 641 forks, 22 open issues, 5 active PRs) reads as a small, well-triaged team rather than a high-traffic repo ([GitHub repo](https://github.com/oqtane/oqtane.framework); [GitHub LICENSE](https://raw.githubusercontent.com/oqtane/oqtane.framework/master/LICENSE)). A secondary aggregator claim of "2322 pull requests from 54 contributors" and "43 official releases" could not be verified against a primary GitHub insights source, and the 43-releases figure looks implausibly low against the observed 2026 cadence alone — treat these specific counts as **low-confidence** ([WebSearch summary, source unclear](https://github.com/oqtane/oqtane.framework)).

## Modules load dynamically in-process, but "no redeploy" quietly means "restart required"

Oqtane's most distinctive engineering claim — installing third-party functionality into a live site — is real but narrower than the marketing framing suggests. A module is an ordinary Blazor component library: it implements a minimal `IModule` interface whose only job is to expose a `ModuleDefinition` metadata object (`Name`, `Description`, `Version`, `ServerManagerType`, `ReleaseVersions`, `Dependencies`, `SettingsType`), and its UI components derive from an abstract `ModuleBase : ComponentBase, IModuleControl` that injects `PageState`/`ModuleState` via cascading parameters ([IModule.cs](https://github.com/oqtane/oqtane.framework/blob/dev/Oqtane.Client/Modules/IModule.cs); [ModuleBase.cs](https://github.com/oqtane/oqtane.framework/blob/dev/Oqtane.Client/Modules/ModuleBase.cs)). There is no separate manifest file format — the `ModuleDefinition` object *is* the manifest, discovered via reflection (`assembly.GetTypes()`) once the module DLL is loaded ([GitHub Discussion #2059](https://github.com/oqtane/oqtane.framework/discussions/2059); [Assembly Loading in Blazor and .NET Core](https://www.oqtane.org/blog/!/11/assembly-loading-in-blazor-and--net-core)). Modules are packaged as ordinary NuGet `.nupkg` files, produced by a dedicated "Package" project generated alongside Client/Server/Shared projects when scaffolding a new module, and made discoverable in Oqtane's in-admin "Available Modules" list simply by tagging the package `Oqtane` on NuGet.org — no described submission review process exists for that path ([Module Management docs](https://docs.oqtane.org/manuals/system/module-management.html); [Build a Module Extension for Oqtane](https://ryanjagdfeld.com/!/7/build-a-module-extension-for-oqtane)).

The dynamic-loading mechanism is genuine .NET plumbing, not a cosmetic claim: Oqtane's own engineering blog describes server-side loading via `System.Runtime.Loader.AssemblyLoadContext.LoadFromAssemblyPath()` (since .NET Core does not auto-load `/bin` assemblies the way classic .NET Framework did), with client-side WebAssembly scenarios instead downloading the assembly as a byte array and calling `Assembly.Load()` — a mechanism the same post admits breaks if a client-side dependency isn't already present ([Assembly Loading in Blazor and .NET Core](https://www.oqtane.org/blog/!/11/assembly-loading-in-blazor-and--net-core)). But despite this real dynamic-loading capability, **installing a module still requires an explicit application restart** before it's usable — this is stated as a hard requirement, not a suggestion, in the official Module Management docs ("you will be asked to compile the module project and then restart") and confirmed bluntly by a maintainer-adjacent GitHub discussion: "You do not load assemblies dynamically and there is no way how to load them without restart" ([Module Management](https://docs.oqtane.org/manuals/system/module-management.html); [GitHub Discussion #1194](https://github.com/oqtane/oqtane.framework/discussions/1194)). For IIS production hosting, restart is triggered via an admin `/admin/system` button or the classic "touch web.config to force a worker-process recycle" trick; a developer-only workaround using `dotnet watch` file-watching on `*.dll` changes exists to simulate hot reload locally, but it is explicitly a dev-time hack, not a production mechanism ([How To Restart Oqtane](https://docs.oqtane.org/manuals/how-to/restart/index.html); [GitHub Discussion #1194](https://github.com/oqtane/oqtane.framework/discussions/1194)). The honest characterization: Oqtane's "no redeploy" pitch means *no rebuild-from-source / no CI-CD pipeline / no server-file-access needed* — you upload a package through a web UI while the site is up — but it is not a zero-interruption hot-swap; a restart is the universally-confirmed final step across every source examined.

Themes follow the identical pattern (see next section), and module database schema uses **EF Core Code-First migrations** with a database-provider-agnostic `EntityBuilder` helper API in current (v2.1+) versions, executed automatically at framework startup by comparing a module's installed version (tracked in a `ModuleDefinitions` table) against its declared `ReleaseVersions` — across every tenant database in a multi-tenant install ([GitHub Discussion #2059](https://github.com/oqtane/oqtane.framework/discussions/2059)). **This directly conflicts with a separate source describing a third-party component called DbUp that executes raw SQL scripts (including a literal `Uninstall.sql`) for module schema changes** ([GitHub Discussion #1744, via ModuleDefinitionController.cs](https://github.com/oqtane/oqtane.framework/discussions/1744)). The research could not resolve this discrepancy from a primary source — the most plausible explanation is a real historical transition (1.x-era DbUp/SQL-script installs superseded by 2.1+ EF migrations, with the SQL-script path possibly still available as an option for SQL-Server-only modules), but this is an inference, not a confirmed fact, and should be treated as **an open discrepancy** rather than resolved. Perhaps more consequential for anyone evaluating Oqtane's extension model: **no source found in this research — official docs, blog, or GitHub discussion — describes any sandboxing, code-signing, or trust-tier security model for third-party module code.** Modules load via `AssemblyLoadContext` into the same process and the same trust context as the host application and every other module; a targeted search for Oqtane-specific commentary on this topic returned nothing relevant ([WebSearch: marketplace security sandboxing](https://github.com/oqtane/oqtane.framework/discussions/732)). That silence is worth flagging explicitly: it's a genuine architectural gap for a framework whose headline value proposition is installing third-party code into a live production site.

## Themes are compiled component libraries, not skins — runtime-swappable only among what's already installed

An Oqtane theme is architecturally a sibling of a module: a compiled Blazor class library implementing `Oqtane.Themes.ITheme`, with a `ThemeInfo.cs` metadata file, a `Theme.razor` component (`@inherits ThemeBase`) as the overall layout, and one or more `Container.razor` components (`@inherits ContainerBase`) that wrap individual module instances — all sharing one namespace by requirement ([Oqtane Themes Developer Guide](https://docs.oqtane.org/dev/themes/index.html); [Themes - Code Structure of a Theme](https://docs.oqtane.org/dev/themes/oqtane-theme-code-explained.html)). CSS/JS are declared as first-class `Resource` objects on the theme's metadata class rather than referenced ad hoc per component, and static assets live under a `wwwroot` subfolder matching the theme's name ([Themes - Code Structure of a Theme](https://docs.oqtane.org/dev/themes/oqtane-theme-code-explained.html)). There is no documented "CSS-only theme" install path distinct from the full compiled-assembly package — packaging, distribution (NuGet `.nupkg`, Marketplace or manual upload), and the underlying install mechanism are identical to modules, right down to the same `PackageName` metadata field used for install differentiation ([Theme Management](https://docs.oqtane.org/manuals/system/theme-management.html)).

The runtime-vs-build-time question resolves into two genuinely distinct operations that the research explicitly separates rather than conflating, and this distinction is the single most important nuance to carry forward: **switching between already-installed themes** for a site or an individual page is a pure runtime, data-driven admin operation — a dropdown selection in Site Settings ("Default Theme," "Default Container," "Default Admin Container") or in a page's Appearance Configuration, picked up on next render with no compile step and no restart ([Site Settings](https://docs.oqtane.org/manuals/site/site-settings.html); [Page Management](https://docs.oqtane.org/manuals/site/page-management.html)). But **installing a brand-new theme package the server hasn't seen before** requires the same application restart as a new module, for the same reason (a new assembly must be loaded into the process) — one community discussion thread quotes a rationale that resonates with a deliberate architectural trade-off rather than an oversight: "restart application is safe, working and clean method how to update application domain," as opposed to attempting dynamic hot-loading of services/controllers ([GitHub Discussion #3390](https://github.com/oqtane/oqtane.framework/discussions/3390)). Theme scoping is genuinely three-tiered — site-wide default, per-page override, and per-module-instance container selection — meaning a single theme package can ship multiple Container variants selectable independently for each module placed on a page, though the exact per-module-instance UI control was not directly confirmed from a fetched screenshot/quote in this pass and rests on inference from the site/page default-container pattern ([Site Settings](https://docs.oqtane.org/manuals/site/site-settings.html); [GitHub Discussion #3851](https://github.com/oqtane/oqtane.framework/discussions/3851)). The core repo ships only two built-in themes (`BlazorTheme`, `OqtaneTheme`), with additional first-party packages (a Bootswatch-based collection, a "Corporate" theme) distributed as separate repos outside core ([oqtane.framework/Themes tree](https://github.com/oqtane/oqtane.framework/tree/master/Oqtane.Client/Themes); [oqtane.theme.bootswatch](https://github.com/oqtane/oqtane.theme.bootswatch)). Because theme/container assignment lives on Site and Page *data* rather than compiled configuration, and every installed theme assembly loads once into the shared process serving all tenants, different sites in a multi-tenant install can run entirely different themes simultaneously as a natural consequence of the data model, not a special-cased feature — though no single Oqtane doc states this as an explicit callout; it's inferred by combining two independently well-sourced facts (per-site theme setting; shared-process multi-tenancy) ([jocheojeda.com](https://www.jocheojeda.com/2025/10/08/understanding-multi-tenancy-in-oqtane-and-how-to-set-up-sites/)).

## No real drag-and-drop, no page-level drafts — the editor is DNN-era portal chrome, not Gutenberg

This is the area where Oqtane's UX least matches its "no-code page composition" marketing. The in-context "Content Editor" is a pencil-icon overlay on the live page that reveals module borders and a small caret menu per module — but every documented interaction is menu/dropdown-driven, not direct manipulation. Repositioning a module uses discrete named actions — "Move Up," "Move Down," "Move to Top," "Move to Bottom," "Move to [pane]" — reached through a caret menu, with **no drag handles, no live drop-zone preview, and no documented free-form dragging anywhere in the current published documentation** ([Content Editor docs](https://docs.oqtane.org/manuals/content/content-editor.html)). Adding a module means opening a gear-icon Control Panel, picking a module type from a categorized list, and setting Title/Pane/Container via form fields in a modal — closer to WordPress's pre-Gutenberg widget-management screens, or classic DNN/portlet systems (unsurprising, given Oqtane's creator also built DNN), than to a block-canvas editor with insertion points ([Adding Modules guide](https://docs.oqtane.org/guides/modules/adding-modules.html)). Layout flexibility is real but constrained: pages are composed of a fixed, theme-defined vocabulary of named "panes" (the default theme reportedly offers "over 20 options ranging from full-width layouts to asymmetrical ratios," but a third-party example theme ships only 3 layouts across 2 named panes, illustrating how theme-dependent that number actually is), riding on Bootstrap 5's grid — panes are not admin-inventable, nestable, or resizable at runtime ([Content Editor docs](https://docs.oqtane.org/manuals/content/content-editor.html); [cre8magic Oqtane Basic theme](https://cre8magic.blazor-cms.org/magic-themes/oqtane-basic/index.html)).

There is **no page-level draft/versioning system** in the sense most modern CMSs offer. "Publish" is a binary visibility toggle (hidden/admin-only vs. public) — a hidden page is still fully live and directly editable in the database, with no separate draft copy that diverges from a published version and no preview-before-live workflow. Direct fetches of both the Control Panel and site-level Page Management docs explicitly confirm "no reference to draft versions, content versioning, or revision history systems" ([Page Management (Control Panel)](https://docs.oqtane.org/manuals/content/page-management.html); [Page Management (site)](https://docs.oqtane.org/manuals/site/page-management.html)). Version history exists only at the individual HTML/Text module level — a "Versions" tab with View/Restore/Delete on past edits — meaning it's fragmented and module-specific rather than a page-wide capability ([HTML/Text Editor docs](https://docs.oqtane.org/manuals/content/html-text-editor.html)). The bundled rich-text editor itself is **QuillJS v1.3.7** — a JS-interop wrapper around an old, pre-2.0 pinned version of Quill, not a modern block-based or ProseMirror/CKEditor-class engine — alongside a peer "Raw HTML Editor" tab, consistent with a classic "content = one HTML blob per module" model rather than structured/JSON block content ([HTML/Text Editor docs](https://docs.oqtane.org/manuals/content/html-text-editor.html)). Notably, the docs frame HtmlText itself as a demo/learning module for exploring the platform's editing mechanics, not a flagship page-building tool. "Templates" in Oqtane are a site/page-provisioning concept — scaffolding starter modules/content at creation time (`DefaultSiteTemplate`, `EmptySiteTemplate`) — not an editor-facing reusable-block/pattern library like Gutenberg's synced patterns; no design-token or theme-variable system is exposed to content editors anywhere in the sources reviewed ([oqtane.org blog: site templates](https://www.oqtane.org/blog/!/92/scalability-testing-and-site-templates)). Taken together, the honest verdict for anyone evaluating whether to borrow ideas here is: **there is nothing in Oqtane's page-editing UX worth adapting** — the requester's own page editor, if it already has drag-and-drop block ordering or a draft/publish split with real staged content, is already ahead of what Oqtane ships.

## Multi-tenancy is a genuine two-tier isolation model, and one narrow piece of it — the alias table — is worth stealing

Oqtane's tenancy model is more sophisticated than a single shared-database-with-discriminator pattern, and it's worth understanding precisely because the report's central transferability question hinges on the distinction. A **Tenant** is fundamentally a named physical database connection — its model doc string reads "Tenants can contain multiple Sites and have all their data in a separate Database," with mapped fields `TenantId`, `Name`, `DBConnectionString`, `DBType` ([Tenant.cs](https://raw.githubusercontent.com/oqtane/oqtane.framework/dev/Oqtane.Shared/Models/Tenant.cs)). A **Site**, by contrast, is a row *inside* a tenant's database, discriminated by `SiteId` — the `Site` model even marks `TenantId` as `[NotMapped]`, because which tenant a site belongs to is resolved by which physical database the row lives in, not by a column value ([Site.cs](https://raw.githubusercontent.com/oqtane/oqtane.framework/dev/Oqtane.Shared/Models/Site.cs)). Oqtane's creator confirmed this directly: "Oqtane supports shared or isolated tenancy. Tenants are managed in the 'master' database and Sites are managed in each individual tenant database" ([GitHub Discussion #979](https://github.com/oqtane/oqtane.framework/discussions/979)). The practical consequence is a genuinely two-tier isolation model: cross-**Tenant** isolation is real database-level separation — separate connection string, separate user store, separate everything — while sites sharing one **Tenant** get only logical isolation: separate content, theme, and settings per Site row, but a *shared user table* ("a Site is a distinct portal that shares its membership with the other portals in the same Tenant") ([Site Management docs](https://docs.oqtane.org/manuals/system/site-management.html)). Whether that same-tenant Site isolation is enforced anywhere below the application layer (e.g., row-level security) versus relying purely on `SiteId`-filtered queries was not confirmed by any source examined — treat same-tenant Site isolation as **query-discipline-based, not database-enforced**, unless proven otherwise.

Request-time resolution is hostname/URL-based via a first-class **Alias** entity, not a session-based site picker: a request's `{scheme}://{hostname}/{path}` is matched against Alias rows carrying both `TenantId` and `SiteId` as mapped columns (with a computed `SiteKey = "TenantId:SiteId"`), and an Alias's `Name` can be a bare domain, a subdomain, or a `domain/path` combination — all three resolution styles supported simultaneously by one mechanism rather than three separate strategies most multi-tenant frameworks would implement independently ([Alias.cs](https://github.com/oqtane/oqtane.framework/blob/dev/Oqtane.Shared/Models/Alias.cs); [Class Alias docs](https://docs.oqtane.org/api/Oqtane.Models.Alias.html)). Non-default aliases redirect to a flagged `IsDefault` alias specifically to avoid duplicate-content SEO penalties — a deliberate design choice worth copying if replicating this pattern, since it's an easy detail to omit ([GitHub Discussion #1947](https://github.com/oqtane/oqtane.framework/discussions/1947)). **This is the one piece of Oqtane's tenancy machinery genuinely worth adapting for a single-tenant app**: a standalone table of `(HostPattern, PathPrefix, IsDefault, TargetSiteOrEquivalent)` rows, resolved by middleware ahead of anything else that needs site context, lets one existing content model answer under multiple domains, subdomains, or path prefixes — for a sub-brand microsite, a partner-branded portal, or dev/prod environment aliasing — without adopting Oqtane's full Tenant/database-switching layer, which is irrelevant to a single-tenant app. This is a narrow, self-contained idea, not an argument for multi-tenancy itself.

On the broader question of how real Oqtane's multi-tenancy is in practice: it is clearly first-class by design intent — tenancy isolation was named explicitly (alongside automated upgrades) as one of DNN's specific weaknesses Oqtane was built to fix ([Oqtane Blog: Oqtane vs DNN](https://www.oqtane.org/blog/!/19/)) — and ongoing permission-system investment (see below) shows real usage pressure years into the project. But no source found states what fraction of real-world deployments actually run multi-tenant versus single-site, and the existence of a multi-part third-party "how to actually set up multi-tenancy" tutorial series as late as October 2025 is weak circumstantial evidence that it is not a heavily-trodden, one-click path for most users ([Joche Ojeda, multi-tenancy setup series](https://www.jocheojeda.com/2025/10/08/understanding-multi-tenancy-in-oqtane-and-how-to-set-up-sites/)) — adoption depth here should be treated as genuinely unknown rather than inferred favorably from design pedigree alone.

## The dynamic permission-policy system is the sleeper idea worth studying closely

Outside modules, theming, and page editing, the single most technically distinctive idea found is Oqtane's **runtime-composed authorization-policy system**, shipped in v3.3.0. Rather than statically declaring every ASP.NET Core authorization policy at startup (the conventional `PolicyNames.ViewModule`/`EditModule` pattern), Oqtane implemented a custom `AuthorizationPolicyProvider` that composes policies on demand from an `"EntityName:PermissionName:DefaultRoles"` string format — usable directly as `[Authorize(Policy = "User:Read:Registered Users")]` on an API method with no pre-registration step required ([Oqtane Blog: Permission Enhancements](https://www.oqtane.org/blog/!/55/permission-enhancements)). This extends fine-grained permission checks from UI/module-instance scope to the entire API surface, and the permission table itself is explicitly generalized — "designed with flexibility in mind so that it can be used with any entity or permission" — with community usage extending it to arbitrary custom entities, such as per-client-record permissions to prevent cross-client data leakage inside a custom module ([GitHub Discussion #2159](https://github.com/oqtane/oqtane.framework/discussions/2159)). For anyone building their own plugin/module system (the requester's own CMS/page-editor context is exactly this shape), this is a reusable pattern worth studying directly: it lets extension authors declare their own fine-grained, role-delegable permissions without the host application having to pre-register every possible policy string at startup — a real solution to a real extensibility problem, not just a policy-naming convention.

Two other ideas are well-executed if less novel. Oqtane's **scheduled-jobs subsystem** gives each background job admin-visible Edit (including a "Next Execution" override), Delete, per-job Log viewing, and Stop controls — a materially higher operational-visibility bar than a typical bare `IHostedService` timer loop — and a real third-party module (`DNF.Projects`) demonstrates the extensibility pattern end-to-end in production, not just as a documented stub ([Oqtane Docs: Scheduled Jobs](https://docs.oqtane.org/manuals/system/scheduled-jobs.html); [GitHub: oqtane/DNF.Projects](https://github.com/oqtane/DNF.Projects)). And Oqtane treats **headless/API-first consumption as a first-class render mode** rather than a bolted-on afterthought: `Site.RenderMode` accepts "Headless" as a peer option alongside Static/Interactive, and Swagger integration for the REST API layer ships by default ([Site.cs](https://raw.githubusercontent.com/oqtane/oqtane.framework/dev/Oqtane.Shared/Models/Site.cs); [oqtane.org](https://www.oqtane.org/)). Several adjacent threads remain explicitly unresolved in the underlying research and are flagged rather than guessed at: the search/indexing technology behind the site-scoped `SearchContent` table was never identified (SQL LIKE vs. a real index engine is unknown); no dedicated sitemap or structured-data feature was confirmed either way; the deeper i18n mechanism behind per-site `CultureCode`/`Languages` fields (resource files vs. DB-stored translations, RTL support) was not investigated; and a claimed "event logging and audit trails" feature was found only in an uncorroborated WebSearch synthesis, never an independently-fetched primary source.

## Conclusion

The clearest signal across all five research threads is a consistent architectural personality: Oqtane invests heavily in the infrastructure a framework author cares about — dynamic assembly loading, a hybrid tenancy model, a generalized permission-policy engine, a headless-by-default API surface — and comparatively little in the surface a content editor actually touches, where it still looks and behaves like 2010s-era DNN portal chrome (menu-driven module placement, a pinned Quill 1.3.7 editor, no drafts, no drag-and-drop). That split is the most useful takeaway for the requester's own single-tenant business-suite CMS: if the goal is a better page-editing experience, Oqtane offers essentially nothing to emulate and the requester's own editor likely already exceeds it; if the goal is extensibility or multi-front-door hosting infrastructure, three ideas travel well in isolation — the `IModule`/`ITheme` interface-plus-reflection extension pattern (accepting that "dynamic loading" in practice still means restart-on-install, a limitation worth designing around explicitly rather than discovering later), the alias table for serving one site under multiple hostnames/paths without adopting full multi-tenancy, and the runtime-composed entity-scoped permission-policy model for any future plugin system. The unresolved discrepancies flagged throughout — EF migrations vs. DbUp for module schema, the stray 2024/2026 release-date mismatch, and unverifiable contributor/release-count statistics — are minor individually but collectively suggest Oqtane's own documentation and secondary write-ups are less internally consistent than its code-level architecture, a reminder to verify against source (not docs) before porting any specific mechanism rather than a specific number.
